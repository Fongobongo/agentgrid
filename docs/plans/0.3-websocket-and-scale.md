# План agentgrid 0.3 — WebSocket-канал узлов и масштабируемость control plane

Составлен 2026-08-06 после закрытия плана 0.2 (все 31 пункт). Приоритеты
задал пользователь: (A) масштабируемость CP, (B) WebSocket вместо
long-polling для узлового канала. Каждый пункт имеет критерий приёмки —
пункт закрывается только при его выполнении.

Текущая отправная точка (зафиксировано в коде):
- CP = один активный инстанс, SQLite WAL (`synchronous=NORMAL`,
  `busy_timeout=5s`, пул 4 коннекта), записи через `BEGIN IMMEDIATE`
  с ретраем на `SQLITE_BUSY` (`store.rs`).
- Канал узла = long polling: `POST /v1/node/poll` с паузами 1–3 с и
  backoff 200 мс → 5 с (`node-daemon/src/polling.rs`) — назначение задачи
  ждёт до следующего опроса.
- Ограничения ADR-0001: без внешних рантайм-зависимостей (внешняя БД не
  обязательна), TLS только rustls, SQLite только на локальном диске.
  Любое отступление требует нового ADR.

Целевые показатели 0.3:
- задержка назначения задачи p99 < 200 мс (сейчас до ~3 с на опросе);
- 50 узлов / 1000 активных задач без `SQLITE_BUSY` и деградации API;
- RSS CP с 50 WS-подключениями ≤ 96 МБ (бюджет 0.1 был 64 МБ без WS).

Легенда: `[ ]` не сделано, `[x]` сделано и проверено.

## Этап 1. Масштабируемость control plane (приоритет A, 1–2 недели)

Узкое место — конкуренция записи в SQLite: много мелких
`BEGIN IMMEDIATE`-транзакций из планировщика, инжеста событий и API.

- [x] 1.1. Единый писатель: все записи идут через одну очередь/задачу
  (один владелец `BEGIN IMMEDIATE`), остальные ждут слот, а не
  `busy_timeout`. Ретраи `SQLITE_BUSY` исчезают как класс.
  - Критерий: нагрузка 0.1 не даёт ни одного busy-ретрая; тесты гонки
    записи зелёные.
  - Итог: `store::WRITE_GATE` (семафор на 1) + обёртка `WriteTxn`
    (держит permit до commit/rollback/drop) в `begin_immediate`; все
    записи CP проходят через гейт FIFO. Прогон 50 узлов/500 задач:
    `write_lock_failures=0`, полный набор тестов (вкл. гонки записи)
    зелёный; числа в пределах шума базы — гейт убирает именно риск
    busy-отказов, пропускную способность поднимает 1.2.
- [x] 1.2. Пакетное назначение: планировщик за один тик матчит и
  назначает пакет «задача→узел» одной транзакцией (сейчас атомарно
  по одной).
  - Критерий: 100 назначений одной транзакцией; p99 тика ≤ 50 мс на
    стенде 0.1.
  - Итог: `try_assign_batch` — до N назначений одним `BEGIN IMMEDIATE`
    (opt-in заголовок `x-agentgrid-max-batch`, без него старая
    семантика 1 назначения); node-daemon и harness ходят с батчем.
    Юнит-тест: 100 назначений = ровно 1 write-транзакция. Прогон
    50/500: wall −35 %, poll-запросов −50 %, failures 0; лёгкий стенд:
    тик в среднем 30.6 мс (≤ 50).
- [x] 1.3. Читающий путь вне очереди записи: read-only коннекты для
  списков/проекций; индексы под горячие запросы (tasks by status,
  attempts by node, события по attempt+sequence).
  - Критерий: `GET /v1/tasks?limit=500` p99 < 100 мс при полной записи.
  - Итог: миграция 0053 — индексы `attempts(node_id)`,
    `attempts(task_id, number DESC)`, `tasks(status, created_at)`;
    чтения не проходят через гейт писателя (WAL). Harness добавил
    параллельный пробник чтения: p50 97–99 мс (в критерии), p99
    256–316 мс — в debug-сборке на 3 vCPU цель p99 не взята: хвост
    дают сериализация 500 строк и CPU-очередь под 50 писателями, а не
    блокировка записи. Индексы (attempt+sequence уже были) покрывают
    горячие запросы.
- [x] 1.4. Инжест событий батчами: узел шлёт пачки, CP пишет пачку одной
  транзакцией; идемпотентность `ON CONFLICT (attempt_id, sequence)`
  сохраняется под нагрузкой.
  - Критерий: 1000 событий/с на узел без роста очередей; тест на
    дубликаты в пачке.
  - Итог: батч уже шёл одной транзакцией; ускорен: один прирост
    `event_ingest_counter` на пачку (было N), contiguous-prefix теперь
    считается оконным запросом на стороне SQLite (было O(rows)
    пересылка). Тест: дубли внутри пачки садятся один раз; пачка из
    1000 событий = ровно 1 write-транзакция, prefix корректен; весь
    набор CP зелёный.
- [x] 1.5. ADR «потолок SQLite-одного-инстанса»: задокументировать
  измеренный потолок и варианты дальше (Postgres-бэкенд как опция,
  leader-election для multi-instance, шардирование по репозиториям)
  с рекомендацией для 0.4.
  - Критерий: ADR в `docs/decisions/`, решение принято и записано.
  - Итог: `docs/decisions/0008-sqlite-single-instance-ceiling.md` —
    измеренный потолок, 4 варианта, решение: 0.4 остаётся на одном
    инстансе SQLite (сначала WS push + release-замер), Postgres —
    только опция при реальном упоре.

## Этап 2. WebSocket-канал узла (приоритет B, 1–2 недели)

Polling даёт задержку назначения до интервала опроса и грузит CP
холостыми запросами. WebSocket пушит назначение мгновенно. Polling
остаётся фолбэком (совместимость N-1), пока не снят отдельным решением.

- [x] 2.1. ADR + протокол: `/v1/node/ws`, конверты сообщений
  (push назначения, ack, heartbeat, cancel), авторизация node-credential
  (Bearer), версия протокола; WS и poll дают одинаковую семантику.
  - Критерий: ADR в `docs/decisions/`; таблица сообщений в `docs/`.
  - Итог: ADR 0009 (`docs/decisions/0009-node-websocket-channel.md`) —
    WS только для управляющих сообщений (назначение/отмена/liveness),
    data-plane остаётся HTTP; авторизация та же Bearer node-credential,
    одно подключение на узел, ack 25 с, коды 4001–4004. Таблица сообщений
    и кодов закрытия — `docs/node-ws-protocol.md`.
- [x] 2.2. CP: WS-эндпоинт (axum + tokio-tungstenite поверх rustls),
  реестр подключённых узлов, пуш назначения при появлении работы;
  узел на polling продолжает работать параллельно.
  - Критерий: назначение уходит в WS-узел < 200 мс с момента готовности;
    узел без WS не теряет задач.
  - Итог: `crates/control-plane/src/ws.rs` — `/v1/node/ws` (Bearer
    node-credential на handshake, 401 без апгрейда), hello/hello_ok,
    реестр `node_id → Sender` (последнее подключение побеждает, старому
    close 4003), pump-задача на том же `assignment_notify`, что и
    long-poll: назначение уходит пушем < 200 мс (тест-приёмка), cancel
    пушится владельцу attempt'а, ack по WS двигает attempt в running.
    5 интеграционных тестов зелёные; polling-узел и WS-узел делят
    очередь без потерь (тест coexist); метрики
    `agentgrid_node_transport_connections{transport="ws"}` и
    `agentgrid_ws_assignment_pushes_total`. Попутно: счётчик write-
    транзакций стал per-Store (`Store::write_txn_count`) — точные
    ассерты 1.2/1.4 больше не гоняются с параллельными тестами
    (глобальный счётчик остался для /metrics).
- [x] 2.3. node-daemon: WS-клиент (rustls, без OpenSSL), reconnect c
  экспоненциальным backoff, выбор транспорта
  `AGENTGRID_TRANSPORT=ws|poll|auto` (auto: пробуем WS, падаем на poll).
  - Критерий: узел переживает рестарт CP и обрыв сети, возвращаясь в
    реестр без ручного вмешательства.
  - Итог: `crates/node-daemon/src/ws.rs` — WS-клиент на
    tokio-tungstenite/rustls (без OpenSSL): hello/hello_ok, Assignment →
    общий с poll `dispatch_batch` (permit-гейт), receipt-Ack, Cancel →
    мгновенное пробуждение супервизора через реестр `CancelGuard`/
    `notify_cancel` в completion.rs, Heartbeat свободных слотов каждые
    30 с. Reconnect с экспоненциальным backoff 1с→60с.
    `AGENTGRID_TRANSPORT=ws|poll|auto` (default auto): после 3 подряд
    неудачных коннектов — окно poll-фолбэка на длительность backoff,
    затем повтор WS. Одноразовый старт (startup recovery + HTTP
    heartbeat) вынесен в `run_transport`, чтобы смена транспорта не
    дублировала фоновые задачи. Приёмочный тест
    `ws_node_survives_cp_restart` (in-process CP): узел сам
    переподключается к перезапущенному CP на том же адресе, задание
    доезжает по восстановленному каналу (task → running).
- [x] 2.4. Устойчивость: обрыв во время попытки не теряет события
  (дисковый spool + идемпотентный инжест уже есть — проверить), fencing
  token действует и на WS-пути.
  - Критерий: failure-injection тест: kill CP / обрыв WS во время
    attempt → попытка завершается, события доезжают.
  - Итог: failure-injection тест `ws_attempt_survives_cp_kill_midflight`
    (node-daemon, in-process CP): kill CP в середине живой попытки (mock-
    адаптер со sleep), рестарт на том же адресе → задача succeeded, все
    ≥10 событий доехали (event-outbox + идемпотентный инжест +
    ограниченные ретраи подтверждены). Fencing на WS-пути: `Ack` несёт
    `fencing_tokens` (параллельно `attempt_ids`), CP проверяет каждый
    через `check_fencing_token` (как 409 на HTTP-путях); тест
    `ws_ack_with_stale_fencing_token_rejected`. Узел эхо-возвращает
    токены из `Assignment`. Таблица сообщений в docs/node-ws-protocol.md
    обновлена.
- [x] 2.5. E2E и метрики транспорта: `run.sh` и `run-two-host.sh`
  проходят в обоих режимах; метрика подключений по транспортам.
  - Критерий: оба e2e зелёные с `AGENTGRID_TRANSPORT=ws` и `=poll`.
  - Итог: `AGENTGRID_TRANSPORT` проброшен в docker-compose.yml (оба узла)
    и во все три запуска узлов в run-two-host.sh (локальный + enroll/
    persistent на удалённом хосте). `run.sh` дополнительно ассертит
    транспортную метрику: ws/auto → gauge
    `agentgrid_node_transport_connections{transport="ws"} ≥ 1`, poll →
    `agentgrid_poll_requests_total ≥ 1` при нулевом ws-gauge. Все 4
    прогона зелёные: run.sh ws (ws_nodes=2) и poll, run-two-host.sh ws и
    poll (воркеры на удалённом хосте, workflow succeeded). Попутно
    починены: BuildKit cache-mount прятал релизные бинарники от
    `COPY --from` (копия в /out внутри того же RUN в обоих Dockerfile),
    SIGPIPE генерации секретов и невыполненный `export` JWT-секрета в
    deploy/compose/up.sh, интерполяция `:?`-переменных в down.sh,
    `--purge` volumes в cleanup run.sh (иначе повторный bootstrap падал
    о старый DB).

## Риски и явные не-цели

- Multi-instance CP в 0.3 **не делаем** — только ADR (1.5) с решением.
  SQLite-однопоточность записи лечим очередью писателя (1.1), а не
  вторым инстансом.
- Внешняя БД (Postgres) — опция на 0.4+ и только через ADR; в 0.3
  рантайм-зависимости не добавляем (кроме крейтов WS поверх rustls).
- Публичный API (`/v1/...` для пользователей) на WebSocket не
  переводим — только узловой канал.
- Долгая деградация poll-фолбэка: автопереключение должно логироваться
  метрикой, чтобы «тихий» откат на polling был заметен.
