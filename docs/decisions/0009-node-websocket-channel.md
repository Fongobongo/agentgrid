# ADR 0009: WebSocket-канал узла `/v1/node/ws`

Status: accepted (2026-08-06)

## Context

Узловой канал сейчас — long polling: `POST /v1/node/poll` держится до 25 с,
назначение уходит в следующий опрос, задержка назначения до ~3 с (план 0.3,
этап 2). Поллинг также грузит CP холостыми запросами: 50 узлов × паузы 1–3 с
= десятки пустых POST/мин, каждый занимает хендлер на время ожидания.

Цель 0.3: назначение уходит в узел < 200 мс с момента готовности, при этом:
- ADR 0001: TLS только rustls, без обязательных рантайм-зависимостей;
- совместимость N/N-1: узлы без WS (старые бинарники, `AGENTGRID_TRANSPORT=poll`)
  продолжают работать параллельно;
- одинаковая семантика: транспорт не меняет поведение (назначение, отмена,
  fencing, идемпотентность) — меняет только доставку.

## Решение

Отдельный WS-эндпоинт `/v1/node/ws` для управляющих сообщений (назначение,
отмена, heartbeat). Весь data-plane (события, завершение, артефакты,
ACP-сессии) остаётся на существующих HTTP POST-эндпоинтах: там уже есть
дисковый spool, идемпотентный инжест, fencing-проверки и метрики, и дублировать
их в WS нет смысла. WS заменяет ровно то, что сегодня делает poll: получение
назначений и обнаружение отмен.

Ключевые пункты:

- **Транспорт**: axum `ws()` поверх rustls (как и весь TLS проекта);
  крейты `tokio-tungstenite`/`axum` без OpenSSL.
- **Авторизация**: та же node-credential, что и на `/v1/node/*` —
  `Authorization: Bearer <credential>` читается из заголовков handshake ДО
  апгрейда; неверная/отозванная → HTTP 401, апгрейда нет. Отдельных
  WS-токенов не вводим.
- **Версия протокола**: узел в `hello` шлёт `protocol_version`; несовместимый
  major (общая `is_incompatible_protocol`, сейчас major "1") → сервер
  закрывает соединение кодом `4002` до любых назначений, узел помечается
  degraded как и на поллинге.
- **Реестр подключений**: в памяти CP — `node_id → Sender<ServerMsg>`
  (последнее подключение узла побеждает, старое закрывается кодом `4003`:
  узел после разрыва сети переподключается, а не двоит назначения).
  Назначение после commit write-транзакции пушится в реестр; узла нет в
  реестре → задача остаётся `queued` и достаётся поллингом (семантика не
  меняется: назначение создаёт запись в `attempts`, WS — лишь транспорт
  доставки, потеря пуша = таймаут узла и повторный запрос назначений).
- **Надёжность пуша**: назначение не считается доставленным до `ack` узла.
  Узел не прислал ack за таймаут (~25 с, как поллинг) — attempt гасится
  существующим reaper'ом и задача возвращается в очередь. Тот же путь, что
  при потере poll-ответа: новых состояний не появляется.
- **Heartbeat**: сервер шлёт WS ping раз в 15 с; отсутствие pong дольше
  45 с → соединение закрывается, запись в реестре снимается. Узел шлёт
  `heartbeat` при изменении свободных слотов, чтобы CP не пушил сверх
  `max_concurrency`.
- **Отмена**: CP пушит `cancel { attempt_id }`; узел отвечает `cancel_ack`.
  Отмена через API для WS-узла идёт тем же store-путём (status attempt'а),
  пуш — только ускорение доставки; узел на поллинге видит её своим путём.
- **Выбор транспорта на узле**: `AGENTGRID_TRANSPORT=ws|poll|auto`
  (по умолчанию `auto`: пробуем WS, при серии неудач handshake/соединения
  падаем на poll; возврат к WS по backoff-циклу). Деградация видна в
  метрике `agentgrid_node_transport_connections{transport=...}` — тихий
  откат на poll недопустим (риск плана).
- **Fencing**: токен генерируется на назначении (в `Assignment`) и
  проверяется на data-plane HTTP-вызовах — без изменений; WS его только
  перевозит.

## Альтернативы

1. **WS для всего канала** (события и результаты тоже в WS). Отказ: пришлось
   бы заново строить spool/идемпотентность/метрики, дублируя проверенный
   HTTP data-plane; выигрыша нет — события и так батчами (0.3 1.4).
2. **gRPC-стрим**. Отказ: новый стек зависимостей (prost/tonic), выходит за
   рамки «rustls + минимум крейтов», пользы для одного потока назначений нет.
3. **SSE от CP к узлу**. Односторонний: ack/heartbeat всё равно нужен
   HTTP-канал; WS симметричен и уже есть в axum.
4. **Оставить поллинг, снизить паузы**. Задержка упирается в паузу опроса;
   холостые запросы растут линейно с числом узлов — цель < 200 мс недостижима.

## Последствия

- Появляются `docs/node-ws-protocol.md` (таблица сообщений) и ADR;
  реализации — пункты 2.2–2.5 плана 0.3.
- Поллинг не удаляется: N-1 совместимость и фолбэк `auto`; снятие —
  отдельным ADR не раньше 0.4.
- RSS CP с 50 WS-подключениями должен остаться ≤ 96 МБ (бюджет из шапки
  плана 0.3); проверяется на этапе 3.
- Метрики: счётчик подключений по транспортам, возраст старейшего пуша
  без ack (опционально) — в 2.5.
