# ADR 0008: потолок SQLite одного инстанса и путь масштабирования

Status: accepted (2026-08-06)

## Context

План 0.3 (этап 1) упёрся в естественный потолок SQLite при одном активном
control plane. Измерено harness'ом (`tests/e2e/run-load.sh`, debug-сборка,
3 vCPU Xeon E5-2699 v4, HDD-класс диск; числа в `docs/load-baseline-0.3.md`):

- стоимость одной write-транзакции ~7.5 мс (debug) → ~31 назначение/с при
  записи по одной; пакетное назначение (0.3 1.2) снижает ЧИСЛО транзакций
  (wall −35 %, poll-запросов −50 % при батче 2), но не стоимость транзакции;
- единый писатель (0.3 1.1) убирает SQLITE_BUSY как класс: отказы записи
  нулевые на всех прогонах, ожидание переехало в FIFO-очередь семафора;
- чтения идут параллельно записи (WAL, вне гейта): p50 списка задач ~98 мс
  под 50 писателями; хвост p99 (~250–320 мс) — CPU/сериализация debug-
  сборки, не блокировка;
- инжест событий уже батчевый: 1000 событий одной транзакцией (0.3 1.4).

Проектное ограничение (AGENTS.md / ADR 0001): один активный control plane,
SQLite только на локальном диске. Вопрос: что делать, когда один инстанс
станет узким местом.

## Варианты

1. **Остаться на SQLite, добить дешёвые рычаги** (WS push назначений —
   этап 2 плана 0.3; дальше: группировка инжеста по времени, реже
   checkpoint, read-реплики через VACUUM INTO/лите-копии для аналитики).
   Стоимость: дни. Потолок записи остаётся ~сотни мелких транзакций/с
   (debug) / тысячи (release), но push убирает поллинг-очередь из задержки.
2. **Postgres-бэкенд опционально** (sqlx уже в зависимостях; Store —
   единственный владелец SQL). Стоимость: недели (миграции, диалекты,
   деплой-зависимость). Нарушает «no required runtime deps», поэтому —
   только опция, не дефолт.
3. **Multi-instance + leader-election.** Не лечит: узкое место — сам файл
   SQLite, второй инстанс лишь добавляет отказоустойчивость, не
   пропускную способность. Полезен отдельно от БД-вопроса, но позже.
4. **Шардирование по репозиториям** (control plane на репозиторий).
   Радикально, ломает кросс-репо workflow и единую очередь; только при
   реальном спросе.

## Decision

**Для 0.4 остаёмся на одном инстансе SQLite.** Сначала этап 2 плана 0.3
(WebSocket push) и релизный прогон harness'а; Postgres рассматривать,
только если релизный замер покажет упор в запись при устойчивой нагрузке
выше ~10 назначений/с ИЛИ парк > 100 узлов. Multi-instance и шардирование
отложены: они не снимают файловый потолок записи.

## Consequences

- дорожная карта записи: батчи (сделано) → push (этап 2) → замер release;
- `/metrics` (`agentgrid_sqlite_write_txns_total`,
  `agentgrid_sqlite_write_lock_failures_total`, poll-счётчики) + harness —
  постоянный инструмент приёмки; любое изменение записи сопровождается
  прогоном `run-load.sh`;
- Store остаётся единственной точкой, где живёт SQL, — это сознательная
  подготовка к возможной опции Postgres без обязательств.
