# ADR 0010: Task-level auto-retry меняет инвариант терминальности

Status: accepted (2026-08-28)

## Context

Базовый инвариант жизненного цикла задачи: «терминальное состояние
необратимо». `succeeded`/`failed`/`cancelled` — конечные точки; повторный
запуск — всегда явная операция оператора (`retry_task`). Это упрощает
state-machine, аудит и рассуждения о задаче.

Конкурентный анализ (hatchet и др.) показал: для хрупких задач
(интеграционные агенты, обрывы сети, гонки в репозитории) удобнее
автоматическая повторная попытка — «неудача ≠ конец, пока не исчерпан
бюджет». Вопрос: как ввести авто-ретрай, не сломав инвариант.

## Решение

Новый атрибут задачи `max_attempts` (default `1` = поведение ровно как
сегодня). Когда попытка **FAILED** и число попыток меньше бюджета,
`complete_attempt` переводит задачу обратно в `queued` вместо `failed`:

- повторная постановка семантически равна ручному `retry_task`: тот же
  путь (обнуление `finished_at`/`error_code`/`assigned_attempt_id`,
  resume-digest после коммита, аудит-запись `retry.auto`);
- **cancelled никогда не ретраится** — отмена остаётся терминальной;
- попытка остаётся `failed` (полный аудит-трейл, счётчик попыток растёт);
- `succeeded` — терминален как прежде.

Инвариант уточнён с «терминальные состояния необратимы» на «терминальные
состояния необратимы, и `failed` может быть *перезапущен* в пределах
бюджета; `succeeded`/`cancelled` — нет». Проверки целостности (неактивная
попытка у терминальной задачи и т.п.) работают на прежних условиях: после
ретрая задача снова `queued`, `assigned_attempt_id = NULL`, активных
попыток нет.

Соседние решения той же сессии (без архитектурного веса, покрыты
CHANGELOG):
- **consensus patch review** — расширяет существующий механизм
  `consensus_group_id` полями `consensus_mode`/`review_of`; ветка коллапса
  сравнивает вердикты вместо SHA патчей;
- **trivial-conflict resolver, convergence-метрики, skill-scanner**
  — локальные дополнения, инвариантов не трогают.

## Consequences

- `failed` больше не означает «навсегда» — оператору нужно смотреть
  `attempts`/аудит `retry.auto`, чтобы отличить авто-ретрай от одноразовой
  неудачи;
- budget по умолчанию 1 = поведение v0.3.7 и старше, обратная
  совместимость без миграций семантики;
- workflow-тик и scheduler не менялись: после авто-ретрая задача снова в
  очереди, DAG ждёт как обычно.
