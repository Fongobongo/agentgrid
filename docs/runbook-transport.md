# Transport Runbook — когда Poll, когда WebSocket

Статус: **v0.3** (2026-08-07). Транспорт = выбор канала для доставки назначений от Control Plane к node-daemon.

## Кратко

| Параметр | `poll` | `ws` | `auto` (по умолчанию) |
|---|---|---|---|
| Задержка назначения | ~1–2 с (каденс опроса) | < 200 мс (push) | пробуем WS → fallback на poll |
| Нагрузка на CP | больше HTTP запросов | меньше трафика | гибридно |
| Устойчивость | максимальная | зависит от сети | WS+fallback |
| Рекомендация | old nodes, консервативно | современный кластер | default |

## Выбор через переменные окружения

```bash
AGENTGRID_TRANSPORT=poll   # только long-polling
AGENTGRID_TRANSPORT=ws     # только WebSocket
AGENTGRID_TRANSPORT=auto   # пробовать WS, fallback на poll после 3 неудач
```

В `docker-compose.yml` передаётся каждому узлу:
```yaml
environment:
  AGENTGRID_TRANSPORT: ${AGENTGRID_TRANSPORT:-auto}
```

## Когда использовать каждый режим

### `poll` — долгостой и устойчивость

- Легаси-клиенты без поддержки WS
- Сети с нестабильным TCP/HTTP proxy-проходом
- Консервативный деплой: проверено временем, минимум сюрпризов
- Low-memory nodes (меньше соединений держать)

Недостатки:
- Задержка назначения ≈ интервалу опроса (по умолчанию 1 с)
- Больше холостых запросов при низком потоке задач

### `ws` — современное производство

- Требование низкой задержки (< 500 мс)
- Кластеры > 10 узлов (меньше HTTP-шума)
- Выделенные каналы к Control Plane (без HTTP-прокси)
- Высоконагруженные системы: батч назначение через WS пушит до N задач за раз

Недостатки:
- Зависит от качества TLS/TCP стека
- Требует support от network infrastructure (upgradeable connections)

### `auto` — золотая середина (рекомендуется)

Попробуйте WS; если коннект не удаётся 3 раза подряд, падает на poll на duration backoff (1–60 с экспонента), потом retry WS. Идеально для:
- Миграции с poll → WS без простоя
- Mix legacy + modern узлов
- Production with fallback guarantee

## Мониторинг метрик

На `/metrics` CP доступны:

```
agentgrid_node_transport_connections{transport="ws"}  # количество WS-подключений
agentgrid_poll_requests_total                         # общее кол-во poll-запросов
agentgrid_ws_assignment_pushes_total                  # всего push через WS
```

Здоровье транспорта:
- WS mode: gauge ≥ 1 при наличии узлов
- Poll mode: poll_requests_total растёт steadily

Пример проверки:
```bash
curl -fsS http://cp:7800/metrics | grep agentgrid_node_transport_connections
```

## Load baseline (измерения 2026-08-07)

100 узлов, 1000 задач, debug binary:

| Transport | Wall time | p50 assign | p99 assign | write_lock_failures |
|---|---|---|---|---|
| auto | 30.4s | 21.3s | 29.5s | 0 |
| poll | 30.0s | 22.7s | 29.5s | 0 |

Разница в пределах шума — fallback корректен. Для снижения p99 нужна пакетная доставка (stage 1.2 batched assignment) или push по WS.

## Связь через промежуточный хост (релей на узле)

Когда узел не видит Control Plane напрямую (firewall, NAT без hairpin, не
открытый peering), но видит другой узел, который CP видит, — второй узел может
пронести трафик первого. Отдельный бинарь ставить не нужно: релей живёт в
`agentgrid-node-daemon` и включается одной переменной.

```
        ┌─────────────┐   нет маршрута   ┌──────────────┐
        │  узел B     │ ───────────────► │ Control Plane│
        │             │                  │              │
        │             │ ───► узел A ───► │              │
        └─────────────┘      релей       └──────────────┘
```

### На узле A (промежуточный хост)

```bash
AGENTGRID_RELAY_LISTEN=0.0.0.0:7900 \
AGENTGRID_RELAY_ADVERTISE=http://10.20.0.5:7900 \
AGENTGRID_RELAY_ALLOW=10.20.0.0/16 \
  agentgrid-node-daemon
```

- `AGENTGRID_RELAY_LISTEN` — адрес релея. Не задан = релея нет (по умолчанию).
- `AGENTGRID_RELAY_ADVERTISE` — адрес, который **объявляется** остальным: его
  подставят в команду подключения нового хоста (см. ниже). С `0.0.0.0` он
  обязателен: `0.0.0.0` значит «все интерфейсы этой машины», а не адрес, по
  которому кто-то может постучаться. Без advertise узел не объявляет **ничего**,
  а не угадывает hostname — угаданный был бы неверен не здесь, а на той машине.
  Если listen задан конкретным IP, адрес выводится из него; путь и не-HTTP схема
  отвергаются на старте.
- `AGENTGRID_RELAY_ALLOW` — CIDR-список источников, которым разрешено
  пользоваться релеем. **Обязателен**, если listen не на loopback: без него
  любой хост, который дотянется до порта, получает дорогу в control plane, и
  оператор расширил периметр, нигде об этом не написав. Loopback — исключение
  (ssh-туннель, локальный sidecar): там список не нужен.
- Релей несёт **только** `/v1/node/*`. Всё остальное — `/v1/auth/*`,
  `/v1/users`, `/v1/ha/*`, админские маршруты — он отвечает `404`, не читая
  тело. Раньше он форвардил весь API, то есть порт релея был вторым входом в CP,
  а скомпрометированный хост-релей видел все креденшлы, которые через него шли.
  Узлу этого достаточно: enroll, `join.sh`, бандл, heartbeat, поток событий
  attempt'а, завершение и WebSocket — всё под `/v1/node/`.
- Upstream не настраивается: релей всегда ходит на *текущий* CP этого узла
  (`base()`), поэтому при смене лидера он переключается на следующем запросе.
  Кластерный токен не нужен.

### Транспорт до релея — открытый HTTP

Плечо «узел B → релей A» идёт по обычному HTTP, и креденшл узла B пересекает его
в открытом виде. Релей не может это исправить на своём уровне: ему пришлось бы
терминировать TLS сертификатом, который проверит клиент узла, а тот доверяет
только системным корням (свой CA он принимает лишь в cred-gateway). Поэтому
требование к слою ниже, и оно обязательное:

- WireGuard (или другой VPN) между узлами, либо
- ssh-туннель до релея (`AGENTGRID_RELAY_LISTEN=127.0.0.1:7900` на A, туннель
  поднимает оператор), либо
- сегмент, где релей и его клиенты — единственные хосты.

Демон пишет предупреждение об этом при старте релея: он не знает, что у вас
внизу, и молчать было бы хуже.

### Добавить хост через релей одной командой

Команду выдаёт CP, а не оператор: только он знает, какие узлы объявили адрес
релея.

```bash
ag nodes add --name behind-nat --via node-a
#   curl -fsSL http://10.20.0.5:7900/v1/node/join.sh \
#     | sudo bash -s -- --token <t> --server http://10.20.0.5:7900
```

`--via` принимает id или имя узла; `ag nodes ls` показывает объявленные адреса
в колонке `RELAY`. `--server` в строке выглядит избыточно (скрипт, скачанный
через релей, и так по умолчанию указывает на него), но по умолчанию там
`AGENTGRID_PUBLIC_URL`, если оператор его задал — то есть ровно тот адрес,
который новый хост не видит. Лишний флаг дешевле установки, падающей на
последнем шаге на машине, куда оператор не зайдёт.

Отказы, и все намеренные: неизвестный `--via` → `404`; **отозванный** узел →
`409` (его креденшл мёртв, значит до CP он не достаёт и никого пронести не
может — в тексте `ag nodes rekey`); узел, который слушает, но ничего не
объявляет → `409` с `AGENTGRID_RELAY_ADVERTISE` (не с той переменной, которую
уже задали); узел, который релеем не является вовсе → `409` с
`AGENTGRID_RELAY_LISTEN`. Токен при отказе не минтуется вовсе (он выдаётся
после того, как релей разрешён). Ти́хого отката на прямое подключение нет:
релей просят **потому что** прямой путь не работает.

`offline` — исключение: это `200` с `status` и `last_heartbeat_at` в ответе,
предупреждение, а не отказ. Узел мог вернуться, пока оператор несёт строку на
ту машину, и отказывать здесь значило бы гадать. Чтобы предупреждение не
превращалось в «поставили и не работает», добавьте `--probe` в строку
подключения — проверка идёт **до** установки:

```bash
curl -fsSL http://10.20.0.5:7900/v1/node/join.sh \
  | sudo bash -s -- --token <t> --server http://10.20.0.5:7900 --probe
```

`--probe` прогоняет только что проверенный по SHA-256 демон против
`--server` и останавливается, если хост туда не достаёт. Через релей строка
`CONTROL PLANE` покажет `hops=1` — это единственный способ отличить релей,
который форвардит, от прокси, который просто слушает.

### На узле B (тот, который не видит CP)

```bash
AGENTGRID_SERVER=http://10.20.0.5:7900 \
AGENTGRID_TRANSPORT=ws \
  agentgrid-node-daemon
```

Всё. `poll`, `ws` и `auto` работают одинаково: релей проксирует HTTP, стримит
SSE и артефакты, и мостит `/v1/node/ws`. На стороне клиента ничего не меняется
— `AGENTGRID_SERVER` уже был точкой настройки.

### Если релеев несколько (резервирование)

С одним `AGENTGRID_SERVER` маршрут ровно один: если A упал, B сообщает о
потере транспорта и идти ему больше некуда — именно это проверяет e2e
(`B reports the loss of its only route`). Автоматически второй релей никто не
ищет: обнаружения нет, список задаётся руками.

Зато у узла уже есть переключение между эндпоинтами — тот же механизм, что
возит HA-реплики CP:

```bash
AGENTGRID_SERVERS=http://10.20.0.5:7900,http://10.20.0.9:7900 \
AGENTGRID_TRANSPORT=ws \
  agentgrid-node-daemon
```

`AGENTGRID_SERVERS` (множественное число) побеждает `AGENTGRID_SERVER`, если
заданы оба. Ротация идёт по кругу с возвратом, поэтому оживший A будет
испробован снова. Переключение срабатывает в `poll`, `heartbeat`, `ws` и при
регистрации — то есть узел переживает падение релея без ручных действий.

**Релей жив, но потерял свой маршрут.** Это отдельный случай, и он опаснее
падения: релей отвечает, но отвечает `502 control-plane unreachable`, потому что
сам больше не видит CP (оборвался аплинк, сгорел маршрут, узел переехал в другой
сегмент). Для узла это не ошибка транспорта — соединение установилось, — поэтому
переключение по `connect`/`timeout` его не видит.

Такие ответы считаются отдельно: после **трёх подряд** `502`/`504` от одного
эндпоинта узел уходит на следующий. Счётчик общий для `poll`, `heartbeat` и `ws`
(они ходят в один и тот же эндпоинт, и три отказа в сумме значат то же, что три
подряд в одном цикле), а любой успешный ответ или смена эндпоинта его обнуляют.
Почему не с первого: единичный `502` — это икота балансировщика, и переключение
на нём дёргало бы весь парк. В логе это видно построчно:

```
poll: control plane answered 502 Bad Gateway — gateway failure 1/3; ...
heartbeat: control plane answered 502 Bad Gateway — gateway failure 2/3; ...
poll: 3 gateway errors in a row from http://10.20.0.5:7900; rotating control-plane endpoint to http://10.20.0.9:7900
```

Если эндпоинт один, идти некуда — узел остаётся и пишет
`no other endpoint is configured`.

Та же логика закрывает **исходящий прокси**: прокси перед мёртвым релеем отвечает
`502`, а не отказом соединения, и раньше это прибивало узел к одному маршруту
навсегда. Теперь он уходит после трёх.

**Чего это не лечит.** Ротация по-прежнему не срабатывает на прочие `5xx`
(`500` — это ответ *самого* CP, переезжать из-за него некуда) и на `4xx`
(неверный креденшл переездом не лечится). И это не обнаружение: список
эндпоинтов задаётся руками, никто не ищет релей сам.

### Что проверить, если не работает

Сначала — с самого узла, который «не видит». У демона есть встроенная
диагностика: ни креденшла, ни enrollment, ни root ей не нужно, и она
отрабатывает до проверки прав, поэтому запускается и на голом хосте.

```bash
agentgrid-node-daemon probe --server https://cp.example.com:7800 \
                            --relay  http://10.20.0.5:7900 \
                            --gateway http://10.20.0.5:7920
```

```
CONTROL PLANE:
  https://cp.example.com:7800  ok     41 ms  v0.8.2 (node protocol v2), hops=0
RELAY:
  http://10.20.0.5:7900        ok      8 ms  forwards, hops=1
```

`--relay` — проверка, которой нет больше нигде: она просит URL провести запрос
*до* CP и читает обратно счётчик хопов, который CP наблюдал. `hops=1` = релей
действительно форвардит. `hops=0` = URL слушает, но не форвардит (обычный
HTTP-прокси, L4-балансировщик или сам CP). Отсутствие заголовка — не отказ:
значит CP слишком старый, чтобы его вернуть, и probe честно говорит «не могу
сказать» вместо того, чтобы покрасить все релеи в красный при откате.

`--proxy` включается вручную: демон уважает `HTTP_PROXY`/`HTTPS_PROXY` для
своего трафика, и probe с унаследованным прокси измерил бы достижимость
*прокси*, а не этого хоста. Код возврата 1, если хоть одна проверка не прошла —
годится для скрипта. Флаги `--server`/`--relay`/`--gateway`/`--host`
повторяемые, `--json` для машинного вывода.

| Симптом | Причина | Что делать |
|---|---|---|
| `409 node "x" is not a relay` на `ag nodes add --via` | узел не слушает вовсе | задать `AGENTGRID_RELAY_LISTEN` |
| `409 ... listens on 0.0.0.0:7900 but announces no dialable address` | слушает, но `AGENTGRID_RELAY_ADVERTISE` не задан | задать его и дать узлу отбить heartbeat |
| `409 node "x" is revoked` | отозванный креденшл: до CP узел не достаёт | `ag nodes rekey` или другой `--via` |
| `404 no node with id or name` на `ag nodes add --via` | селектор не совпал ни с id, ни с именем | `ag nodes ls` |
| probe `--relay` → `hops=0` | URL слушает, но не форвардит | указать порт релея, а не CP |
| probe `--relay` → `stamped no hop` | CP не вернул `x-agentgrid-relay-hops` | не ошибка: CP старше 0.8.2 |
| `403 peer not in the relay allowlist` | источник вне `AGENTGRID_RELAY_ALLOW` | добавить подсеть B; счётчик `agentgrid_edge_rejected_sources_total` растёт |
| демон A не стартует: `would forward to itself` | `AGENTGRID_SERVER` узла A указывает на его же релей | релей должен смотреть на CP, а не на себя |
| демон A не стартует: `bind the peer relay` | порт занят | другой порт или освободить |
| B регистрируется, но задачи не идут | задача не привязана к B | это не релей: назначение выбирает CP |
| `503 no control-plane leader` от релея | A сам потерял CP | смотреть транспорт A, не релей |
| в логе `gateway failure 1/3`, потом `rotating ... to <другой>` | A отвечает `502`: он жив, но не видит CP | проверить маршрут A до CP; узел ушёл сам |
| `502 ... no other endpoint is configured` | эндпоинт один, идти некуда | задать `AGENTGRID_SERVERS` списком |

Счётчики релея — на его же `/metrics`:

```bash
curl -s http://10.20.0.5:7900/metrics | grep agentgrid_edge_
# agentgrid_edge_requests_total          — сколько запросов прошло
# agentgrid_edge_ws_bridges_total        — сколько WS-сессий проброшено
# agentgrid_edge_rejected_sources_total  — сколько хостов отбито allowlist'ом
# agentgrid_edge_upstream_errors_total   — сколько раз CP не ответил
```

### Границы

- **Цепочка собирается без настройки.** Релей форвардит на `cfg.base()` — тот CP,
  с которым *этот* узел говорил бы прямо сейчас. Узел, которого несёт релей B,
  имеет `base()` = B, поэтому он может нести следующего: C знает только B, B
  знает только A, и запрос проходит оба хопа. Ни одна переменная топологию не
  описывает. От бесконечного кольца (два релея друг на друге) защищает счётчик
  хопов: `x-agentgrid-relay-hops` + `AGENTGRID_RELAY_MAX_HOPS`, по достижении —
  `508`. E2E — `tests/e2e/run-relay-chain.sh` (в CI: «relay chain (two relays,
  hop counter, 508 on a loop)»).
  *(Раньше здесь было написано «один хоп, цепочка не поддерживается» — это
  перестало быть правдой с появлением счётчика; ошибка была в том, что ADR
  описывал протестированное, а не возможное.)*
- **Видно, кого несёт релей.** `GET /v1/nodes` отдаёт `relay_hops` — сколько
  релеев прошёл последний heartbeat; в панели это бейдж `via relay ×N`, в
  `ag nodes ls` — колонка `REACH`. Число **наблюдает** CP из заголовка, который
  релей заменяет своим, поэтому узел не может заявить меньше, чем прошёл.
  Заголовок ставит **любой** форвардер, включая отдельный `agentgrid-cp-edge`
  (`max_hops = None` теперь значит только «нет лимита», а не «не считать»),
  поэтому `relay_hops: 0` = «в пути нет форвардера AgentGrid». L4-балансировщик
  или сторонний HTTP-прокси этим не покрываются — на L4 ставить некуда.
  CP возвращает наблюдённое значение в `x-agentgrid-relay-hops` на **каждом**
  ответе (всегда, включая `0`), так что клиент может проверить свой путь сам —
  на этом стоит `probe --relay`; а отсутствие заголовка означает «CP старше
  0.8.2», а не «ноль хопов».
  Подробнее — `docs/agent-ops.md`, «Is this node connected directly?».
- **`relay_url` — это заявление, а не факт.** Узел объявляет адрес
  (`AGENTGRID_RELAY_ADVERTISE`), CP его не проверяет: релей существует ровно
  для того, чтобы до него доставали те, кто не достаёт до CP, — то есть у CP
  нет способа это проверить по построению. В `ag nodes ls` это колонка `RELAY`,
  `-` = «не релей»; по ней резолвится `--via`.
- **`relay_listen` отделён от `relay_url` намеренно.** Раньше `0.0.0.0:7900` без
  advertise выглядел ровно как «не релей», и оператор шёл задавать переменную,
  которую уже задал. Теперь узел сообщает и адрес привязки, и в `RELAY` видно
  `:7900 (no advertise)` — релей запущен и никем не используется; лечится
  `AGENTGRID_RELAY_ADVERTISE`. Обе величины — заявления узла.
- **Это не обход авторизации.** `Authorization` передаётся как есть, CP
  по-прежнему аутентифицирует собственный креденшл узла B. Обходится только
  сетевая сегментация — ради чего всё и делается.
- **`/metrics` и `/health/*` релея перекрывают одноимённые пути CP** на этом
  порту (тот же компромисс, что у отдельного `agentgrid-cp-edge`).
- **HA-репликация CP** через релей не проверялась: теоретически можно указать
  peer URL на релей перед лидером, но это не покрыто тестами.

Полное обоснование — `docs/decisions/0026-relay-through-an-intermediate-host.md`.
E2E-сценарий — `tests/e2e/run-relay.sh` (в CI: «peer relay»).

## Troubleshooting

### Node не подключается по WS

1. Проверьте логи: `grep "error.*connect\|reconnect" /tmp/node.log`  
2. Убедитесь, что порт 7800 доступен и не заблокирован firewall  
3. В `auto` режиме fallback сработает автоматически — проверьте poll metrics

### Высокий `write_lock_failures`

Увеличите `busy_timeout` в config SQLite OR переходите на пакетное назначение (batch assignment). Это лечится stage 1.2.

### RSS превышен

CP idle = 4 MB при 50 WS-коннектах ≤ 96 MB budget. Если превышает — проверьте утечки в логах (`tracing::warn!`, heap allocation spikes).
